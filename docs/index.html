Spec DialogueThe dialogue is the work. The document is its crystallized output.

Six phases, checkpoints an autonomous caller cannot skip, a seven-dimension quality gate, a panel of skeptics prompted to kill the spec, and an explicit human sign-off. What leaves at the end is a pair of documents: the specification, and the acceptance tests that decide whether it was met. It writes no code and runs no tests.

01The dialogue, including the way back

The forward path is the easy half. What this figure exists to show is the return edges — where a circling dialogue, a gate finding and a successful refutation each send the work. Every phase boundary carries a checkpoint, and a checkpoint is part of the contract rather than a mode setting: an autonomous caller stops at it too.

A confirmed checkpoint is not a rubber stamp. A checkpoint presentation fits about fifteen lines and shows the delta since the last turn, because an unreadable checkpoint produces a confirm that means nothing — which is worse than no checkpoint at all.

02When this is the right skill

Spec Dialogue is deliberately heavy on interaction turns. That heaviness buys the thing it exists for — a specification whose every load-bearing element someone actually agreed to — and it is the wrong price for a change whose shape is already settled.

Use it when

  • a feature idea exists but is not yet buildable, and the user wants to think it through in conversation
  • the deliverable needed is a specification with acceptance criteria — not code, not a verdict
  • several plausible directions exist and the choice between them should be made deliberately
  • a locked spec needs revising because reality moved

Use something else when

  • the user wants code now and the shape is already settled — this skill writes none
  • the open question is which feature to build at all — decide that first, then spec the winner
  • the deliverable is a whole-repository architecture document rather than one feature
  • an existing feature needs excavating and explaining — that is archaeology, not specification

03Depth scales the dialogue, never the lock

Forcing a settings toggle through six phases makes people abandon the skill and specify nothing. Depth is the release valve — and it is carefully drawn so that the valve releases turns and nothing else.

DepthWhenPhasesPanelTurns
lightone bounded change, the problem is already agreed, no real option spaceFRAME → SPECIFY → LOCK, the middle three collapsing into one confirmskipped~3–5
standard defaulta normal feature with genuine alternativesall six2 skeptics — claims 1 and 3~8–15
deephigh-stakes, contested, or expensive to reverse; a spec several teams will build againstall six, with an extended EXPAND4 skeptics — one per claim~15–30
The invariant. Testable acceptance criteria, a test case behind every must-have one, the Quality Gate, the Provenance Gate and an explicit sign-off are lock preconditions at every depth. A light run that discovers a real option space escalates to standard and says so, rather than under-specifying quietly.

04The six phases

Each phase names lenses — a framing question plus an output shape — not tools. Adopt them in sequence yourself, or spawn them as parallel subagents if your harness has them; the recipe is correct either way. Dashed chips are conditional. Nothing here requires a specific agent, model or tool to exist.

PHASE 0FRAME

Problem before solution

Establish the shared problem statement before any option is generated. On an existing codebase, survey what already ships first — a spec that re-derives shipped code is the expensive kind of wrong.

  • Demand
  • Research-grounding?
  • Persona?
  • Reuse-scan?
Checkpoint · mandatory

A 3–5 line problem statement, carrying the reuse and constraint findings. The user confirms or corrects it. Option generation cannot start until it is confirmed.

writesthe draft is created: status draft, L0 filled

PHASE 1EXPAND

Diverge before converging

Run Divergence twice with different framings — once proposing, once reframing the assumptions or borrowing from another domain. Produce 3–5 candidate directions, each with a rationale and a rough shape.

  • Divergence ×2
  • Market?
Checkpoint

The user reacts, eliminates, combines, adds. Expect several turns here — this is the divergent heart of the dialogue. Keep the questions polarity-neutral: a leading question contaminates the data.

writesthe surviving candidates

PHASE 2CHALLENGE

Stress-test, then converge

Narrow to one direction under four distinct pressures — is it necessary, is it over-scoped, is it feasible, and how does it fail.

  • Arbitration
  • Subtraction
  • Impact
  • Pre-mortem?
Checkpoint · mandatory

The user makes the explicit pick. Rejected directions are carried forward as “considered but rejected” so a resume never re-derives them. If the dialogue circles for two rounds with no new information, it offers a choice rather than looping.

writesthe pick, and the rejected list

PHASE 3SHAPE

The structured proposal

Synthesize the chosen direction: problem → proposed solution → in scope → out of scope → assumptions → open questions.

  • Proposal
  • Prioritization?
Checkpoint

Edits are captured section by section, then written — not summarized back and assumed.

writesthe agreed sections

PHASE 4SPECIFY

Authoring, and the tests that decide it

Staged elaboration: L0 Vision → L1 Requirements → L2 Detail → Behavior matrix → L3 Acceptance Criteria. The acceptance test specification is written alongside L3, not after it — writing the procedure is what exposes a criterion that only reads as testable, while it can still be rewritten.

  • Authoring
  • Verifiability
  • API-detail?
  • Data-model?
  • Demand?
Checkpoint

Iterate section by section. Every criterion is a Given / When / Then scenario with a named oracle — the thing that decides pass or fail. Every result in the test document is authored NOT_RUN.

writesboth documents, incrementally

PHASE 5LOCK

Sign-off, and nothing else

The independent Quality Gate, then the refutation panel, then the user's explicit sign-off. On sign-off both documents are promoted to locked together, the build path is chosen with the user, and the Handoff Packet is emitted as a recommendation.

  • Adversarial-review
  • Verifiability
  • Skeptic ×2–4
  • Arbitration?
Checkpoint · mandatory

Sign-off is the user's, never the agent's. The build-path choice is contract-level and cannot be auto-picked, even under an autonomous caller.

05What leaves at the end

Two documents, locked together. They rot on different clocks — the criteria change when the feature changes, the procedures change when the environment or the tooling does — so folding them into one would let an environment note edit the acceptance contract. Every section is present, or marked N/A with a one-line reason; a required section may not be N/A, a conditional one may.

docs/specs/<slug>.md — the specification

  • L0 Vision req — problem, audience, job, success definition, existing assets and constraints
  • Glossary req — one concept one term, with a not to be called column so synonym drift is a grep rather than a feeling
  • L1 Requirements req — REQ-n and CFR-n; every cross-functional row carries a metric, a target and how it is measured
  • L2 Detail cond — four fixed slots: data model, interface contract, state and transitions, validation rules
  • Behavior matrix req — the six conditions a spec forgets, each row citing a requirement and a criterion
  • Dependencies · Migration & rollout cond — what we do not control, and the point past which a change stops being reversible
  • L3 Acceptance Criteria req — Given / When / Then, verification mode, oracle, must-have flag
  • Scope · Considered but rejected req
  • Assumption Ledger · Open Questions req — ASSUME-n and OQ-n, each with an owner and a level
  • Build-path decision req

docs/specs/<slug>.acceptance.md — the acceptance tests

  • Test scope — including what passing this suite still does not prove, stated up front rather than discovered at ship
  • Entry & exit criteria — the acceptance contract in one list. Anything not on it will not block acceptance
  • Environment — build, data state, roles, flags, each dependency live or stubbed, clock and locale
  • Test data — fixtures and their reset procedure, which is what makes a second run the same suite as the first
  • Test cases — TC-n with concrete step values. “Enter a valid email” is not a step
  • Non-functional procedures — one per CFR-n, its target cited from the spec, never restated
  • Coverage matrix — the AC → TC half of the chain, with both gap directions named
  • Defect handling — severities, and which of them block exit
  • Execution record — authored empty; a re-run appends, so a flaky case is visible instead of overwritten
  • Residual risk · Sign-off
The test document decides nothing the spec left open. Writing a case and finding no stated behaviour for an expired token does not license a decision there — it produces an OQ-n in the spec. A test document that answers its own questions is a shadow spec, and the build will follow whichever of the two it read last.

06Two hops, four directions

The coverage claim is only checkable if it is a link rather than a paragraph. IDs are stable and never renumbered: a revision supersedes — REQ-004_v2 — so a reader holding the old ID can find out what happened to it.

07The Spec Quality Gate

A seven-dimension review of the spec as an artifact, by a reviewer that is not its author. Independence is load-bearing: the author never scores its own gate. Where no separate agent is available, the gate runs as a distinct pass with the authoring context set aside — read as a stranger would, from the document alone. Each dimension must pass, or its finding is explicitly downgraded into Open Questions. Never silently passed.

DimensionThe question it asks
AmbiguityIs any requirement or criterion open to more than one reasonable interpretation?
CompletenessDoes every in-scope requirement have at least one criterion, and every must-have criterion at least one test case? Both hops.
ConsistencyDo scope, requirements and criteria contradict each other anywhere?
TestabilityIs every criterion verifiable by a machine or a human — with a named oracle, not “verifiable in principle”?
Scope coherenceAre in-scope and out-of-scope collectively exhaustive and mutually exclusive?
ProvenanceIs every load-bearing element elicited, ratified or parked — none silent?
ResolvabilityDoes every UNKNOWN, TBD and open assumption appear in Open Questions with an owner and a level — and is nothing left at before-build?

and the document rules underneath them

The seven dimensions decide whether the spec is right. A separate set of rules decides whether it can be read and trusted: a declared audience and decision, freshness metadata with a review trigger, every externally-checkable fact grounded or flagged, UNKNOWN over a plausible guess, one fact stated in exactly one place, one concept one term, and every template section present. Both are lock preconditions.

08The pre-lock refutation panel

The seven dimensions audit the spec as a document. They do not ask the harder question: should this be locked at all? A spec that is internally consistent, fully traceable and completely wrong passes every one of them. So 2–4 independent skeptics run before sign-off, each prompted to kill the spec from one assigned angle rather than to evaluate it — a skeptic asked to evaluate will hedge.

Claim a locked spec silently assertsThe skeptic's angle
The problem is realthe stated pain is assumed, not evidenced — no user, telemetry or research anchor backs it
This direction beats the rejected onesa direction dropped in CHALLENGE is strictly better under the stated constraints — re-opened against the final scope, which moved after the pick
The criteria prove the requirementsAC-n passes on an implementation that does not satisfy REQ-m
The scope boundary holdsan out-of-scope item is load-bearing for an in-scope requirement — the boundary is not actually separable
Kill weak claims, not bold ones. Refuted-on-evidence — a comparable feature already ships, the cited pain is contradicted by measured behaviour, a criterion demonstrably passes on a non-conforming build — sends the spec back. Unproven-because-new is the signature of a genuine novel bet, not grounds for rejection; it routes to LOCK-with-flag, the flag naming the assumption it rests on and, where possible, the observation that would falsify it after ship. Penalizing a feature for lacking proof that can only exist post-launch is the exact failure this protocol guards against.

never decided on a panel vote alone

Safety-critical scope — auth, encryption, input validation, anything with a regulatory obligation — is not cut from a spec on a skeptic's vote; a panel does not authorize removing a control. Below 60 % confidence, the destructive reading is not acted on. And a verdict flips on new evidence, never on pressure: objection from the author, the user or a louder panel member is not a refutation. Name the triggering evidence, or do not flip.

09What actually blocks a lock

A locked spec is not a spec with no unknowns. It is one where every unknown has an owner and a level — and where nothing that must be settled before a build begins is still open. The skill names three of the rows below as the lock preconditions proper — testable criteria, a procedure behind each, and the Quality Gate; the rest are the gates and the sign-off standing around them. All seven stop a lock.

10The Handoff Packet

A handoff that ships only a file path forces whatever builds the feature to re-derive what the dialogue already settled. The packet carries the settled state in consumable fields, emitted at LOCK as a recommendation, not execution.

FieldWhat it carries
spec_paththe locked specification
acceptance_criteriathe criteria with Given / When / Then, requirement mapping, mode, oracle and must-have flags — the build's completion contract
acceptance_test_paththe locked test document, every result NOT_RUN; its exit criteria are what “done” means
behavior_matrixthe error paths the build must not invent for itself
glossaryso the build names things the way the spec does
non_goalsthe out-of-scope list, verbatim
dependenciesintegration points, their contracts, and the declared fallback for each
assumption_ledger · open_questionswhat is still open, with owners and levels — never silently dropped downstream
refutation_flagseach LOCK-with-flag claim and the assumption under it — a kill-criterion candidate for the build
reuse_findings · build_pathso the build skips re-scanning, and knows how it was meant to run
The contract rule cuts both ways. A build that receives the packet does not re-open the settled decisions — it may surface a contradiction it discovers against real code, but re-litigating the direction is drift. And a build that finds a must-have criterion unbuildable as written returns for revision, re-entering at SPECIFY and re-running the lock preconditions, rather than quietly reinterpreting it.

11How the questions are asked

The dialogue is the work, so the question craft is part of the recipe rather than a matter of style. Sixteen rules govern it; these are the ones that change the transcript most.

  • One focus per turn. One question, or one batched multiple-choice over at most four independent dimensions. Never a wall of open questions — each extra question halves the answer quality of all of them.
  • Recognition over recall, and no leading. Offer concrete anchors to react to rather than asking someone to produce an answer from nothing, and keep the polarity neutral: a leading question contaminates the data it collects.
  • Paraphrase back before persisting. A vague answer is probed, not swallowed. What gets written down is what the user recognised as theirs.
  • The Assumption Ledger. Every gap the user did not explicitly decide — a skipped question, a vague answer, a default chosen to keep moving — is recorded as ASSUME-n. Open entries never quietly disappear; at LOCK each is ratified or moved to Open Questions.
  • Envelope, and delta only. About fifteen lines per checkpoint, showing what changed since the last turn plus an orientation line. The full state lives in the draft the user can open.
  • Depth follows signal. Rich answers earn finer questions; answers trending shorter earn batching, proposed defaults and more of the Ledger. Matching the user's bandwidth is part of the contract, not a courtesy.
  • The Provenance Gate. Every load-bearing element of the locked spec is elicited, ratified or parked. An element that is none of these is silent, and a silent element blocks the lock.
  • The reader's language. Both documents are written in the language the user is conversing in. The IDs, metadata keys, enum values, paths and code identifiers stay verbatim, because something downstream cites them.

12Install and invoke

The skill lives at skills/spec-dialogue/. That directory is what gets linked — the repository README and the test battery stay behind. Three CLIs read a SKILL.md with YAML frontmatter and each looks somewhere different, so make link writes one symlink per CLI installed on the machine; one whose own directory does not exist is skipped rather than created, and inside a project codex and agy share .agents/skills, so a single link there serves both.

install

make link                      # every agent CLI installed here
make link AGENT=codex          # just one — claude | codex | agy
make link PROJECT=/path/repo   # that repository, instead of the home directories
make status                    # where is it linked?
make unlink                    # remove the links that point at this repo
agentglobalinside a project
claude~/.claude/skills<repo>/.claude/skills
codex$CODEX_HOME/skills, default ~/.codex/skills<repo>/.agents/skills
agy~/.gemini/config/skills<repo>/.agents/skills

Nothing at a destination is overwritten: a real directory, or a link into another checkout, is refused and left alone, and make unlink removes only the links pointing at this repository. SKILLS_DIR=<dir> overrides the destination outright for a runtime none of the three names.

invoke

spec-dialogue                      # new dialogue
spec-dialogue depth=light          # small, bounded change — fewer turns, same lock
spec-dialogue depth=deep           # high-stakes or contested — full skeptic panel
spec-dialogue resume [<slug>]      # re-enter from the last checkpoint
spec-dialogue <slug-or-path>       # re-open a locked spec for revision

the checks that keep the skill honest

make check   # every cited path resolves inside the skill; no path reaches through
             # a parent; no file in reference/ that SKILL.md never names; the lens
             # and gate-dimension counts the prose claims match what is defined
make test    # the fixture battery — each check is broken in a scratch copy and
             # required to fail, so a check nobody has watched fail is not trusted;
             # `make link` runs there too, against a throwaway home directory
Resumable by design. The value here is a long multi-turn dialogue, so it must survive interruption. Each checkpoint writes to docs/specs/<slug>.draft.md with a current-phase marker and the Assumption Ledger delta. spec-dialogue resume replays the marker, summarizes the decisions so far in a few lines for confirmation, and continues — never silently restarting from FRAME.
